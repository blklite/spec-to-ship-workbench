# wb: the stage machine

`python -m wb` runs stages 2 to 5 of an item ([process/stages.md](../process/stages.md)) through the runner core ([runner/README.md](../runner/README.md)). No model is inside it: each model call is 1 short step, and a wait costs nothing. The owner acts only at the stops.

The stage machine has a local-file tracker, runs its tests on the fake runner, and runs on a host: a detached run, the push of each branch, the secret guard and a wrapper for each Claude step ([The host](#the-host)).

## Commands

```sh
python -m wb intake <spec> --id <id> [--branch <branch>] [--repo <name>]
python -m wb run-next <id> [--foreground]
python -m wb answer <id> --file <file>
python -m wb hold <id> (--reason <text> [--after <id2>] | --clear)
python -m wb approve <id> <merge|live|high> [--head <sha40>]
python -m wb status [<id>] [--json]
python -m wb pages --out <dir> [--answer-url <url>]
python -m wb pull-answers --queue <dir>
python -m wb record <id> <pr|gate|merge|follow-up> [options]
python -m wb notify
python -m wb deliver <id> [--foreground]
```

| Command | Does | Last line |
|---|---|---|
| `intake` | Checks the spec against [docs/specs.md](../docs/specs.md): the size limit `specs.max_kb`, each header line and section, the tier, the size and its 3 limits, a *Proof:* for each AC, and no open-question mark (a `## Open questions` heading, or `TBD` or `TODO` as a whole word, outside code). It prints 1 line for each problem. A pass creates the tracker item and the state at stage 2. A new intake of a waiting item replaces its spec and starts the spec check again; it voids each approval, and keeps the steps, the dollars, the time and the rework rounds used. `--repo <name>` names the repository of the item: a key of `[repos]` in the config. The state holds the name and its URL as `work.repo` and `work.url`; with no `--repo` a new item has null for both (the origin of the code clone) and an amendment keeps the old values, as `--branch` does. An unknown name is 1 problem line that lists the known names. A new intake that changes `work.url` while the work folder of the item exists is 1 problem line that names the folder: the owner deletes a wrong work folder by hand. A change of `work.url` drops the origin and the base commit recorded for the old repository, and its last push: `run-next` records them again from the new work folder | `WB: INTAKE OK <id>` (exit 0) or `WB: INTAKE REFUSE <id> - <n> problems` (exit 1) |
| `run-next` | Starts the run in a new session, detached from the terminal (stdin is the null device), with its log `run.log` in the item folder, and returns. The run holds an OS lock on `run.flock` of the item folder for the whole run (`fcntl.flock` on POSIX, `msvcrt.locking` on Windows; the file stays), then takes the lock of the item, makes the work folder when it does not exist, and runs steps until the item waits or is ready. A held OS lock or a live lock refuses a second run (exit 1), and the OS lock lets only 1 of 2 runs replace the lock of a dead run. An error (an `Exception`) after the lock, while the item on disk is `running`, makes it wait (case 2) with `The run stopped with <class>; the log is <run.log path>.`, never the error text; then the error goes on as before (a usage error exits 2). `--foreground` runs here and prints the result line: the detached run is `run-next <id> --foreground` | `WB: STARTED <id> - log <path>` or `WB: RUN REFUSE <id> - a run is going (pid <n>)`, or `WB: RUN REFUSE <id> - a run is going` when the run that holds the OS lock has not written its lock yet; the log, and `--foreground`, end with `WB: READY <id>` or `WB: WAITING <id> - case <n>: <question>` |
| `answer` | Stores the owner's answer in the item folder, adds it to the inputs of the next step, and sets the item running. It refuses an item that does not wait, a wait for `wb approve`, a wait after a spec-check question and a budget stop: these resume only after a new `intake` of the amended spec (with raised limits, for a budget stop). It holds an exclusive OS lock on `answer.flock` of the item folder from the load of the state to the save of the answer (`fcntl.flock` on POSIX, `msvcrt.locking` on Windows; it waits for another holder, and the file stays), so that 2 answers that overlap give 1 answer and 1 refusal; an unknown id takes no lock, and an error of the lock is a usage error. Each answer, also of `pull-answers`, adds `{"file", "case", "time"}` to `records.answers` | `WB: ANSWER OK <id>` or `WB: ANSWER REFUSE <id> - <reason>` |
| `hold` | Queues a wait below the owner's work on the state page of `pages`: on a waiting item that is not a case 3 or 4 wait, with no live run (`run.lock`), it sets `question.queued` to `{"reason": <text>, "after": <id2> or null}` and saves the state. The reason is the text with its white space joined: 1 to 200 characters. `--after <id2>` names the item that the wait waits for: the hold moves back to "Needs your input" when the owner feed lists `<id2>` in `done`. `--clear` removes the key (with no hold, nothing changes). It holds the lock on `answer.flock` of `answer` from the load of the state to the save, changes no other field and makes no tracker call. A new wait, `answer`, `pull-answers`, `approve <id> high` and a new `intake` each end the hold with the wait. A bad id, or `--clear` with `--reason` or `--after`, is a usage error | `WB: HOLD OK <id>` or `WB: HOLD REFUSE <id> - <reason>` (exit 1) |
| `approve` | The only way an approval enters the state. It refuses when stdin is not a terminal, and asks the owner to type the item id. The head is the last head of the item for `merge` and `live`, and the head of the work folder for `high`; the prompt `Approve <kind> of item <id> at <sha40> (<source>). Type the item id: ` names it and its source, and the approval records it with the time. A given `--head` must be 40 hex characters and equal that head, else it refuses (`the head is not the last head of the item (<sha40>)`, or `the head is not the head of the work folder (<sha40>)`). An item with no head (no step head for `merge` or `live`; no work folder, a folder that is not the top of a git work tree, or no commit for `high`) refuses with or without `--head`: `the item has no head yet: wb run-next makes it`. A later head voids a merge or live approval. A `high` approval lets a High tier item start its build. It does not merge | `WB: APPROVE OK <id> <kind> <sha>` or `WB: APPROVE REFUSE <id> - <reason>` |
| `status` | 1 line for each item: stage, status, rounds, dollars and hours against the limits. With an id: `repo=<name>` on the first line when the item names a repository, each step, the open question, what is not verified, the approvals and, when the item has records, 1 line `  records: ` with the count of answers, the pull request number, the count of gates, the merge sha, the follow-up ids and the diff size (or `diff=error`). `--json` gives dollars, tokens (input, cache read, cache write, output) and seconds by stage and by role | |
| `pages` | Writes read-only HTML pages of the state to `<dir>`, for a job that builds them every 15 minutes and copies them to a folder that the site viewer serves: `index.html` (the build time, the count of the item folders, the count for each status, `unreadable` and each stage, each count above 0 linked to its breakout page, and the 4 sections of the owner's work below), 1 breakout page for each status and each stage with items (`status-<name>.html`, `stage-<name>.html`: id, stage, status, rounds, dollars and hours against the limits, in id order) and `results.html` (the key figures, 4 graphs, then the measures: throughput, cost and time, quality and waits). A spec-check wait shows the question batch of its reply: the text after the last `#` heading with `Questions`, else the full reply. The build reads the state home and the `counters.json` of the run folders with no write and calls no network service; a figure that neither gives shows `no data`. Each text from the state and the owner feed is escaped, and the pages hold no script but the 2 theme scripts (with a theme key), no external URL but the ADO and pull request links of the item ids, and no form without `--answer-url`. **Links and times.** Each item id (a breakout row, a wait heading, "Needs merge", "Steps outside wb" and the Item column of `results.html`) is escaped text. With `pages.ado_url` set, an id of ASCII digits with no leading 0 links to `<ado_url><id>`: `<a href="<ado_url><id>">id</a>`. Next to the id, after 1 space, an item with a known pull request gets `<a href="https://github.com/<owner>/<repo>/pull/<n>">PR <n></a>`: `n` is the number of its PR record (`records.pr.number` of `wb record <id> pr`, an integer above 0), else the feed's `pr`, and the repository is `remote.url` of the item on GitHub; with no number or no GitHub remote there is no link. `pages.ado_url` is private: set it in the local config only. A window of N days is (build time - N days, build time]; for 7 and for 30 days: `Delivered` (the items at stage `delivery` whose last step end is in the window), `USD` (the sum of the step `usd` of `counters.json` whose `end` is in the window; `0.00` with no step), `Median hours to ready` (of the `ready` items whose last step end is in the window: the median of that end minus the `start` of step 1; an item with no `start` is left out) and `Rework-free` (of the Delivered items with a known `rounds_used`, the whole percent with 0, rounded down: `66 %`), then `Waiting now` (the `waiting` items). USD and hours have 2 decimals; a median or a percent with no input shows `no data`. Then 4 graph cards, each 1 inline SVG (`wb/charts.py`: no script, no link, colour only from the tokens `--series-1` to `--series-6` and `--mark`, each 3:1 on a card; `Delivered per week`, `Budget use` and `Waits` take their height from the row count, `USD per week by role` has 1 fixed height for any row count) in a box `chart-box` that scrolls sideways on a narrow screen, as the chart keeps a width of at least 35rem and its 12-unit labels, with its table right below: `Delivered per week` (the 12 ISO weeks up to the build week, oldest first, 0 for an empty week; Week, Items, Item ids), `USD per week by role` (the same 12 weeks, 1 column per week; the step `usd` stacked by role, bottom first, in the order `spec-checker`, `builder`, `reviewer`, `second-reviewer`, `rework`, `other`, where `other` is a step with no known role; a step with no `end` is left out; a negative or not finite `usd` draws no segment, and the axis ends at the largest column sum of the drawn segments, so each column stays in its chart), `Budget use` (the 20 items with the latest last step end, newest first: USD and hours used against `limits.usd` and `limits.hours` as whole percents rounded down, 2 bars per item, a mark line at 100 % and an axis that ends at 200 % while the text keeps the true percent; a missing or 0 limit shows `no data` with no bar) and `Waits` (each waiting item, longest wait first, as `<id>: case <n>`; with no last step end, no bar and `no data`). A graph with no rows shows `None.` and no SVG. **The look.** Each page has 1 header bar with the State and Results links, the build time and the theme buttons Light, Dark and System. On `index.html` the counts are tiles in a grid, and the 4 sections and the Status and Stage counts are cards; on `results.html` the key figures, each graph and each group of measures are cards; each Stage and Status cell of a table is a badge with its text, and a table scrolls in a box under its header row. Each colour is a custom property, light and dark, each text passes WCAG AA, and on a phone the page has no sideways scroll. **The theme.** `wb/theme.py` holds byte-for-byte copies of the 2 scripts of the page shell of the site viewer, with a slot in place of the key literal of the stored choice. The build puts `pages.theme_key` of the config in that slot, so the CSP of the site viewer (a SHA-256 for each script) allows the scripts, and the pages and the wiki share 1 stored choice. The key is private: set it in the local config only, never in a file of the repo. A value that is not 1 to 64 letters, digits, `.`, `_` and `-` is a usage error that leaves `<dir>` as it was, and the message does not quote it. A change of 1 byte of a script, or another key, stops the scripts under that CSP. With no key (no `[pages]` table, or `theme_key = ""`), the pages hold no script and no theme buttons. When the scripts do not run, the page follows the light or dark mode of the system and the theme buttons stay hidden. **The owner's work.** Right after the `Items:` line: 1 line with the count of each section and the time of the owner feed, or `No owner feed.`, then 4 sections. "Needs merge": each `ready` item that is not in `done`, with its id and a link `PR <n>` to `https://github.com/<owner>/<repo>/pull/<n>` (the PR record, else the feed's `pr`, and `remote.url` of the state), or `No recorded PR.` when neither gives a number or `remote.url` is not GitHub, and no second PR link; with no feed, `No owner feed: merges are not known.` and no list. "Steps outside wb": 1 line for each step of the feed, its id and text. "Queued": the other holds of `hold`, each wait block with `Queued: <reason>` after its heading. A wait block is the same in each section, and an empty section has 1 `No ...` line. Each section sorts by the count of held waits whose `after` is the id (most first), then the feed's `priority` (1 first), then its `created` time (oldest first), then the id; a missing value sorts after the known values of its key. **Commands.** With rows in `[[pages.commands]]` of the config (`label`, `host`, `folder` and `command`, each a string and each required; `folder` may be empty; at most 30 rows), `index.html` ends with 1 card `Commands` after its 2 notes: 1 line for each row in config order, the host in bold at 1.125rem, the label, then the copy text `cd <folder> && <command>` (or `<command>` with an empty folder) in a block `copy` that 1 long press selects whole with no script (`user-select: all`) and that wraps on a phone with no line break in the copy. With no rows there is no card. A case 3 or 4 wait shows, after its question, `At the host terminal of <b><host></b>:` with the host of `pages.wb_host` (empty or missing: `At the host terminal:`), then the line to copy: `<wb_command> approve <id> high` for case 3, `<wb_command> answer <id> --file <file>` for case 4, where `<wb_command>` is `pages.wb_command` (empty or missing: `python -m wb`); the owner replaces `<file>` after the paste. A wait of another case but 2 (case 1, for example) keeps `This step is done off the page, at the host terminal.` The copy text and `pages.wb_command` are 1 line of 1 to 300 printable ASCII characters (0x20 to 0x7E) with no leading `$` and no space at either end; `label`, `host` and `pages.wb_host` are 1 to 80 printable ASCII characters. Each text is escaped. The rows and the 2 keys name hosts: set them in the local config only. A bad value is a usage error that names its row number or key, never the value, and leaves `<dir>` as it was. **The owner feed.** `owner-feed.json` in the state home: an optional file that any program of yours may write (a temp file, then a rename); with no file, the pages show no merges and no steps outside `wb`; the build reads it and calls no network service. A JSON object of at most 1 MB (1024 × 1024 bytes): `written` (an ISO time), `done` (the ids of the items whose work is merged or closed), `items` (id: `{"priority": <number>, "created": <ISO time>, "pr": <integer>}`, each key optional) and `steps` (at most 50 of `{"id": ..., "text": ...}`). A missing file, a file above 1 MB, bad JSON or a bad top-level field gives no feed; an entry of a wrong type is skipped, a `steps` list above 50 gives no steps, a time with no zone is UTC, and the build goes on. **Answer forms.** A case 2 wait with no `spec_questions` has options when the last line of its reply starts `BUILD: BLOCKED` or `REWORK: BLOCKED`: the unbroken run of 2 or more lettered lines right before that line (blank lines between the run and that line do not count), and no options when a letter repeats; the page shows 1 line for each. No other wait gets a form, and `<url>` is the only form target. An item folder whose `state.json` cannot be read, has another `version`, or has no `stage` or `status` name counts as `unreadable`, and the build goes on. The build writes a temp folder in the parent of `<dir>` and replaces `<dir>` only after a full build; a missing state home or parent, a `<dir>` that is a file, a `<dir>` inside the state home or an item folder or that holds one, or a `<dir>` with files that a build did not write is a usage error and leaves `<dir>` as it was. Each build lists its pages in `.wb-pages`: a `<dir>` is replaced only when it is empty, or holds only plain files that the list names. It prints nothing on success | |
| `pull-answers` | Reads each `*.json` file at the top of `<dir>` (not a name that starts with a dot, not a folder): `{"id": ..., "qhash": ..., "option": ...}`, from a form of `pages --answer-url`; the writer of the queue writes a file under a name that starts with a dot, then renames it. A file whose `qhash` and letter match the options of the current case 2 wait answers the item with the option line, through the code of `answer`, and moves to `<dir>/done` (a taken name gets a number). For a known id it holds the lock on `answer.flock` of `answer` from the load of the state to the save; an error of the lock is a usage error, and the file stays in `<dir>`. Any other file (above 4096 bytes, not a JSON object of exactly these 3 strings, a bad or unknown id, an item that does not wait or waits at case 1, 3 or 4, a wait that `answer` refuses, a wait with no options, another `qhash` or letter, a link or another file that is not a regular file) is deleted, since it can hold a key, and `<dir>/refused/<name>.reason` gets 1 reason line that quotes nothing of the file. A name in `done` and `refused` keeps at most the first 200 bytes of the part of the queue name before `.json`, cut at a whole UTF-8 character, then `.json`, the number and `.reason`. It never stores or prints a key. It does not start the next step: `run-next` does | `PULL: answered=<n> refused=<m>` (exit 0); a `<dir>` that is not a folder is a usage error |
| `record` | The main session records at the host what `wb` does not see: `pr --number N` (1 to 9 digits, no leading 0) sets `records.pr`; `gate --host-passed P --host-failed F --review "CODE-REVIEW: ..." --reviewer CLOSE\|REWORK --mutants K/N [--second "CODE-REVIEW: ..." --second-seconds S]` adds 1 entry to `records.gates` with the pushed head (null before a push): P, F and K are ASCII digits, N is 1 or more and K at most N, each review line is a full `CODE-REVIEW` line whose 4 counts add to the findings, S is a finite number of 0 or more (digits, an optional fraction, an optional exponent), and `--second` and `--second-seconds` come together; `merge --sha S [--time T] --by main\|owner` sets `records.merge` (S: 40 hex characters, stored in lower case; T: a real time `YYYY-MM-DDTHH:MM:SSZ`, default now; `main` is the main session, `owner` the owner); `follow-up --item M` adds the item id M to `records.follow_ups` once (a known M writes nothing). A new `pr` or `merge` record replaces the old. It holds the lock on `answer.flock` of `answer` from the load of the state to the save, and refuses a live run (`run.lock`). A bad value, a missing option or an option of another kind is a usage error that writes nothing. No MCP tool runs it | `WB: RECORD OK <id> <kind>` or `WB: RECORD REFUSE <id> - <reason>` (exit 1) |
| `notify` | Sends the event lines to the owner's phone; a cron job runs it each 2 minutes. **The lines.** Each change appends 1 line `{"v": 1, "time", "kind", "item", ...}` to `events.jsonl` of the state home, each text cut at 200 characters, in 1 write under an OS lock (`wb/events.py`); a failed append warns on stderr and never stops `wb`. The kinds and their keys: `wait` (`case`, `text`, `key`: the first 16 hex characters of the SHA-256 of the case, 1 line feed and the text) at each wait, `step_failed` (`role`, `status`, `reason`) at each step with no outcome, `budget_alert` (`limit`: `usd`, `time` or `rounds`), `ready` (`tier`), `build` at each builder step, `intake` after `WB: INTAKE OK`, `merge` (`sha`, `by`) after `record merge` and after the merge record of `wb deliver`, and `stop` (`text`: the reason, `key`: as for a wait, of `stop`, 1 line feed, the last head of the item, 1 line feed and the reason) at each `STOP` of `wb deliver`, so that each new `STOP` of an item alerts and the same one alerts once. **The run.** It holds `notify.flock` of the state home (held: `WB: NOTIFY BUSY`, exit 0), reads the whole lines after the offset in `notify-state.json` (a tail with no line feed waits; a bad line is skipped and counted) and runs `notify.command` with no shell for each push, 1 JSON object `{"title", "body", "priority", "tags", "click"}` on stdin (`click`: `notify.page_url`, or `null` when it is empty), with a limit of 60 s, then saves the state: a failed send keeps the cursor. The first run starts at the end of the file and marks the digests that passed as sent. **Needs you** (`wait`, `stop`, `ready` of High tier): 1 push for each item and key (else kind), `high`, tags `warning`, title `#<id> waits: case <n>`, `#<id> stopped` or `#<id> ready for your merge`, body the text (else the title), and 1 reminder `#<id> still waits` after `notify.remind_hours` while `state.json` still shows that wait, or that `ready` with no merge. **FYI** (each other kind): 1 push `low`, tags `workbench`, title `Workbench: <n> updates`, lines `#<id> <kind>` (at most 20, then `and <n> more`), at most each `notify.fyi_minutes`. **Quiet hours and the digest**, in `pages.time_zone`: a Needs-you line whose event time or run time is in `notify.quiet` is held, a reminder due then is dropped, and a reminder due out of it that a run in it finds waits for its end. The first run at or after each time of `notify.digests` sends 1 digest, also with no event: `default`, tags `workbench`, title `Workbench digest <HH:MM>`, lines `Building: <n>`, `Waiting for you: <n> (#<ids>)` (the waiting items and the held lines), `Merged since the last digest: <n>`, `Merged but not live: not known` and `Step spend today: $<x.xx>` (the `usd` of each `counters.json` whose `end` is today). It marks the held lines sent; a missed digest goes once, late. An empty `notify.command`, a `notify.page_url` that is not empty and not an https URL that ends with `/`, or another bad `[notify]` value is a usage error, and the message does not quote the value | `WB: NOTIFY sent=<n> held=<n> skipped=<n>` (exit 0), `WB: NOTIFY BUSY` (exit 0) or `WB: NOTIFY FAIL <reason>` (exit 1): the reason names the exit status or the timeout, never the command or its output |
| `deliver` | The chain after `ready`, with no model, for an item with status `ready` (another status stops with 0 calls). It starts `deliver <id> --foreground` detached, as `run-next` does, with its log `deliver.log` in the item folder, after the check of the id and of the types of `[deliver]` (a bad type is a usage error). The run holds the lock of `run-next` to its end, so `record` and `run-next` refuse. Each setting that the run needs is checked before its first call. In order: until the gate passes, the work folder check (its `HEAD` is the head, with no change that is not in it, as before a review; else `STOP` with 0 calls); the push check (`pushed` is the last head and `git ls-remote` of the recorded origin gives it, else `STOP the head is not pushed`); the pull request (the open one of the branch to the base, else a new one; a pull request to another base is never taken; a new number is recorded as `record pr`); the host test (exit 2 with `refusing: no host-test slot`: wait `retry_seconds`, try again, up to `slot_seconds` from the first call (the busy calls count too; the code review and, at Medium and High tier, the second review (green is a `CODE-REVIEW` line with 0 critical, 0 high and 0 medium; a medium finding stops for a rework round; the second review may end `UNAVAILABLE`, which the gate judges and a new run asks again until the gate passes); the gate (the stdout of `gate_source` is `delivery_check.py` in the folder of the head, run with this Python: 1 `record --file <folder>/checks.jsonl --sha <head> <check> <result>` for `tests`, `self-check` (the `SELF-CHECK` line of the last build or rework reply), `code-review`, `reviewer-review` (the last line of the last review step) and `second-review`, 1 `record ... --from-host-test <host-test output>`, then `gate --item --branch --tier --spec --repo --base`; green is exit 0 and `DELIVERY-CHECK: PASS <branch> head=<head>`, then a `record gate` with the `MUTANTS` line of the last review reply); the merge (Low or Medium tier: the secret guard on the text, then the merge of the pull request only at the gated head, with the title of the pull request and the body `Item <id>.`, the gate line and the head, then `record merge --by main`; when the forge refuses the merge but the pull request is merged at the gated head (the reply of an earlier call was lost), its merge sha is taken; a High tier item, a guard hit or a head that moved waits, case 2); and the ADO calls (`ado` + `state <id> <review_state>`, `field <id> <tracker.subagent_cost_field> <file of the dollars>`, `comment <id> <file>` with the merge sha, the gate line, the 2 review lines and both outputs, HTML-escaped). It makes no follow-up record and no item. `deliver/<head>/` of the item folder holds the output of each call and 1 marker for each call that is done: a new run skips them (a record of `delivery_check.py` only with the same result), and a merged item gives `MERGED` with 0 calls. The first red result ends the run; the status stays `ready`. The merge record writes the `merge` event and a `STOP` the `stop` event of `notify` | `WB: DELIVER <id> STARTED - log <path>`; the log, and `--foreground`, end with `WB: DELIVER <id> MERGED <sha40>`, `WB: DELIVER <id> WAIT <reason>` or `WB: DELIVER <id> STOP <reason>` (a missing or empty list: `STOP deliver.<key> is not set`) |

A usage error (a bad argument, config or state (a `[repos]` key that is not a name of letters, digits, `-` and `_`, or a value that is not a GitHub clone URL), or a work folder that is not a git work tree) prints `wb: <message>` on stderr and exits 2.

## The MCP server

`python -m wb.mcp` serves MCP over stdio (JSON-RPC 2.0, 1 message for each line), so that any MCP client with any model can be the front end while the script enforces the stages. The [plugin](../plugin/README.md) starts it through ssh. Install it on the host as `~/.local/bin/wb-mcp`, a symbolic link to [scripts/wb-mcp](../scripts/wb-mcp) of the code clone: `ln -s <code clone>/scripts/wb-mcp ~/.local/bin/wb-mcp`. The script puts `~/.local/bin` first on `PATH`, because ssh gives a PATH without it and the steps that the server starts must find `claude` there; then it goes to the code clone and runs `python3 -m wb.mcp`. On a host where `claude` is not in `~/.local/bin`, set `PATH` in the ssh command: the last argument in `.mcp.json` becomes `PATH=<folder of claude>:$PATH ~/.local/bin/wb-mcp`.

| Tool | Arguments | Does |
|---|---|---|
| `wb_status` | `id` (optional) | `wb status [<id>]` |
| `wb_intake` | `id`, `spec`, optional `repo` | Writes the spec text to a new file under `specs/` of the item folder, then `wb intake <file> --id <id>`, with `--repo=<repo>` when `repo` is given; a `repo` that is not a name of letters, digits, `-` and `_` (with no leading `-`) is an error before any write. It amends a new item or a case 2 wait only: it refuses a wait of case 1, 3 or 4 before it writes, since an amended spec could raise the limits, lower the tier or clear the round limit; the owner amends those at the host terminal |
| `wb_answer` | `id`, `answer` | `wb answer <id>` with the answer text; it also refuses a case 4 wait, which the owner answers at the host terminal |
| `wb_run_next` | `id` | `wb run-next <id>`: it starts the detached run and returns at once |

Each tool returns the output of its command. There is no approve tool: no tool approves, merges or runs a shell, so no front-end model can approve; `wb approve` runs at the host terminal only. A bad id, a missing argument or a refusal gives a result with `isError` true and 1 line: the last line of the command (for a refused intake, then each problem), or the usage error, with each path outside the item folder replaced by `<path>`; never a traceback. The config is read at each tool call.

## The item folder

Each item has 1 folder under `state.home` (git ignores the default): `state.json`, `tracker.json` of the local tracker, `answers/` and `runs/<n>-<role>/` with the prompt, `counters.json`, `stdout.txt` (the raw output of the CLI), `reply.txt` (the text of each turn of the reply; a Claude step only) and `stderr.txt` of each step, `run.log`, `run.lock` and `run.flock` of the detached run, `answer.flock`, the OS lock of `answer` and `pull-answers` (it stays), `guard.txt`, the last scan file of the secret guard, and `uncommitted.txt`, the paths of the last wait for changes that are not in `HEAD` (a check that finds no such change removes it). A write of a JSON file goes to a temp file, then a rename. A state with an unknown `version` is an error.

`records` in `state.json` holds the metrics of the item; a state with no `records` reads as `{}`, and each key is there once its first record is. `answers`: 1 `{"file": "<nnn>.md", "case": <case of the wait>, "time"}` for each answer. `pr`: `{"number", "time"}` of `record pr`. `gates`: 1 entry for each `record gate`, `{"head": <pushed head or null>, "time", "host": {"passed", "failed"}, "review": {"findings", "critical", "high", "medium", "low"}, "reviewer", "mutants": {"killed", "total"}, "second": {<the 5 counts>, "seconds"} or null}`. `merge`: `{"sha", "time", "by"}` of `record merge`. `follow_ups`: the item ids of `record follow-up`. `diff`: written by `wb` each time the status becomes ready, from `git diff --numstat <remote.base_sha>...<pushed>` in the work folder: `{"base", "head", "files", "added", "deleted", "time"}`, where a binary file counts as 1 file and 0 lines, or, on a git error, `{"base", "head", "error": <1 line of at most 200 characters>, "time"}` and no wait; the last ready wins. Each `time` is UTC, `YYYY-MM-DDTHH:MM:SSZ`.

The work folder of an item is `<work.home>/<id>`: a git work tree. When it does not exist, `run-next` makes it before the first step: a clone of `work.url` of the item, or of the `origin` of the code clone (the clone that runs `wb`) when `work.url` is null, the branch from `origin/<branch>` when the origin has it (a work folder that was lost: the next push is a fast-forward), else from `origin/<base>`, and `user.name` and `user.email` of the code clone in the local git config of the work folder (a step home has no git config). When the folder exists and `work.url` is set, its `origin` must be `work.url` (the same string, as the local config holds it, with no `insteadOf` rewrite): else the run stops with a usage error that names both URLs, before any step, and the owner deletes the folder by hand. The push and the base of the scan follow the `origin` of the folder (below). The branch is `feature/<id>`, or the `--branch` of the intake; the base is `work.base`. A wrapped step also gets `<work.home>/<id>.step/`: `home`, a new step home, and `inputs`, the copies of its inputs. A folder with no write bit in the old step home gets `u+rwx` before the delete.

## The prompt of a step

An Inputs block (the item id, the spec, the work folder, the branch, the base, the paths of the earlier replies that the step needs, and the owner's answers), then the stage prompt byte for byte. Replies pass by path: the path of `reply.txt` of the run folder when it exists, so that a report stays when a late notification opens 1 more turn, else of `stdout.txt` (another adapter, or a run folder from before `reply.txt`). The script reads only the status and the last line of a step, never a reply. A step whose runner has a `wrap` does not see the state home: before the step, the script copies the spec, the replies and the answers into `<work.home>/<id>.step/inputs/`, and the Inputs block names the copies.

| Stage | Role | Prompt | Earlier replies |
|---|---|---|---|
| spec check | `spec-checker` | [spec-check.md](../prompts/spec-check.md) | none |
| build | `builder` | [build.md](../prompts/build.md) | the last spec check |
| review | `reviewer` | [review.md](../prompts/review.md) | the last build, and the last rework after it |
| review, Medium and High tier | `second-reviewer` | [code-review.md](../prompts/code-review.md) | as the reviewer |
| rework | `rework` | [rework.md](../prompts/rework.md) | the review replies of the last review round |

The role map (`config/personas.toml`, else the example) gives the runner of each role.

## Transitions

| Step | Last line | Next |
|---|---|---|
| spec check | `SPEC-CHECK <id>: GO` | build |
| spec check | `SPEC-CHECK <id>: QUESTIONS - <n> questions` | wait (case 2) until a new `intake` |
| build | `BUILD: READY <sha>` | the push (below), then review; a `<sha>` that is not the head of the work folder waits (case 2) |
| build | `BUILD: BLOCKED - <reason>` | wait (case 2) |
| review | `REVIEW: CLOSE`, and the second review has 0 critical and 0 high findings | ready |
| review | `REVIEW: REWORK - <n> blocking`, or critical or high findings of the second review | rework; at the round limit, wait (case 4) |
| rework | `REWORK: DONE` | the commit and the push (below), then review, and 1 rework round is used |
| rework | `REWORK: BLOCKED - <reason>` | wait (case 2) |

- A step with a status other than `OK`, or with a last line that does not fit the item (another item id, `REWORK - 0 blocking`), runs once more; then the item waits (case 2) with its reason.
- When the runner of the second review is `UNAVAILABLE`, the second review is recorded as not verified, never as a pass, and the review goes on.
- A High tier item waits before its build (case 3) for `wb approve <id> high`.
- **The interrupted step.** Before each step the state holds the open step (its run folder, the head before it, the start time). When the lock of the item names a dead PID (after a reboot), the next `run-next` ends the open step `FAILED` with the reason `interrupted`, resets the work folder to the head before the step (`git reset --hard`, then `git clean -fd`), records that its dollars and time are not known, and the rule above applies: the step runs once more. A dead run with no open step only gives up its lock.

## The push

The build agent commits and stops; it does not push. After `BUILD: READY <sha>` the script checks that `<sha>` is the head of the work folder and that the work folder has no change that is not in `HEAD` (a modified file or an untracked file; the review reads the work folder, so it must be the pushed tree; files that git ignores do not count; `git status` runs on a temporary index in the item folder, from `read-tree HEAD`, so a change behind `--skip-worktree` or `--assume-unchanged` waits (case 2) with its path and no content; the question gives the instruction first, then at most 10 paths, sorted and without duplicates, then `and <n> more`, and names `uncommitted.txt` in the item folder, which holds all, 1 line for each path; a path with a character below U+0020, U+007F, `"` or `\` is written in its quoted form, as `json.dumps(path, ensure_ascii=False)` gives it, in that file and in the question; a check that finds no change removes the file), then pushes `<sha>` to `refs/heads/<branch>` of the GitHub repository of `origin` over https (the origin URL and the base commit are recorded in the state before the first step, because a later step can rewrite `.git`; a work folder with no `origin` or no `origin/<base>` waits before any step; no `--force`, never to the base branch), and opens 1 pull request through the GitHub REST API (base `work.base`; a branch with an open pull request gets no second one). The rework agent does not commit: after `REWORK: DONE` the script runs `git add -A` and commits with the message `fix: rework round <n> (item <id>)`, then pushes again; a rework with no change makes no commit, and pushes only a head that is not pushed yet (after a failed push and an answer); with a head that is pushed, it still runs the check of changes that are not in `HEAD`. The token comes from the file `delivery.push_token_file` (an absolute path, mode 0600 on POSIX) and goes only to the push (in the environment of that git process) and the API calls: never into a step's environment, command line, prompt or run folder, and never into an error text. A failed push or API call (an `http.client.HTTPException` too) waits (case 2). **The retry of the push.** When the stage is build, the last step is a build with `BUILD: READY <sha>`, `<sha>` is its head after and the head of the work folder, and the last push is not `<sha>`, `run-next` runs no step: it runs the push again, before the budget stop; a pass goes to review, a failure waits (case 2). A head that changed after `READY` runs the build again, and a new intake starts at the spec check. A build or rework step can write the `.git` of the work folder, so each git command of the script there runs with no hook (`core.hooksPath`, `--no-verify`), no fsmonitor and no replace ref (`--no-replace-objects`: a push sends the real objects), and only when `.git` is a folder with no `info/grafts` or `shallow` file, with no `info/exclude` rule (a link, or a line that is not blank and not a comment; a missing file passes), whose local config holds only the keys that a clone and `run-next` write (read with `--null`: a subsection can hold a space); another key (a filter, `url.<x>.insteadOf`, `include.path`, `core.sshCommand`) waits (case 2). The state is saved after each step, with the dollars and the time of the item, before its push: a death in the push leaves no open step, so no reset throws a finished build away.

## The secret guard

Each runner table takes `guard` (`true` or `false`); it is on by default for each adapter except `fake`, and the counters of each step record it. Before each step of a guarded runner, and before each push whatever the runner, the script writes a scan file in the item folder: the diff of the work folder against the recorded base commit (untracked files too, through a temporary index that starts from `HEAD`, so that a tracked file that `.gitignore` matches shows its new content, and binary files as text), the patch of each commit since the base (a merge against each parent, by `--diff-merges=separate`, whatever `log.diffMerges` says; a secret that a later commit removes still goes out with the push), the commit messages since the base, and for a push the title and body of the pull request. After the diff, the scan file holds each regular file under the work folder, outside the top `.git`, that the temporary index does not hold after `git add -A` (by `.gitignore`, `info/exclude`, a global excludes file or a nested git folder): the whole file as text (a NUL becomes a space), any size and type, no skip by name, at the place `an ignored file, <path>:<line>`; a link gives its target path as text (1 place for each line) and is never followed, and a Windows junction counts as a link (also for the `.git` of the work folder and for the caches); a file or folder that the script can not read waits (`the secret guard did not run`). Before the scan (after the check of `.git`), the Python caches go, with no skip by name and no `.gitignore` read: a regular file `*.pyc` directly in a folder `__pycache__`, and in a folder `.pytest_cache` the regular files `CACHEDIR.TAG`, `README.md` and `.gitignore` at its top and each regular file under `v/`; then each such folder that is empty, with the empty folders in it. A path in `HEAD` or in the real index stays, a file outside these forms stays and is scanned (in a cache folder too), no link is followed, and no removal enters the top `.git` or a nested git folder; a failed removal waits. Of the diff and of each patch, the scan file holds the headers and the added lines, without their `+` marker; a context line and a removed line are empty lines. Both are in the base commit, which is already on the remote, or are added lines of an earlier commit patch: the push sends nothing new with them, and an old hit in the base does not stop an item that edits a line near it. For the same reason a hunk header ends at its second `@@`: the text after it is a line that git copies from above the hunk. Then it runs `scripts/secret-scan.sh --message <file>` of the code clone, with a bash that it finds itself (`WORKBENCH_BASH`, else Git Bash on Windows, else `/bin/bash`) and with `WORKBENCH_DENYLIST` unset. Exit 1 waits (case 2) with the class and the place of each hit (`<path>:<line>` of the diff or of a commit, a commit message, or the pull request text), never the matched text. Any other exit, or no bash, waits too.

## The host

The stage machine runs on a host with no ssh step: the code clone holds `config/workbench.toml` with absolute paths (wb does not expand `~`): `state.home` and `work.home` outside each clone (`work.home` with no symbolic link), and `delivery.push_token_file`. The owner runs `python -m wb` in the code clone over `ssh -t`; a run goes on after the ssh link drops. Nothing starts at boot.

Each Claude step runs in [scripts/wrap-step.sh](../scripts/wrap-step.sh), a bubblewrap wrapper ([process/sandbox.md](../process/sandbox.md)): `wrap = ["<code clone>/scripts/wrap-step.sh", "write"]` for build and rework (the work folder is writable), `"read"` for the spec check and the review. It shares the network, binds the system paths, named `/etc` files and the CLI read-only, the work folder, the step home and the inputs, and nothing else: no `~/.ssh`, `~/.config`, `~/.claude`, state home, code clone or env file. It clears the environment and sets `PATH`, `HOME`, `TMPDIR`, `LANG`, `DISABLE_AUTOUPDATER` and `CLAUDE_CODE_OAUTH_TOKEN`, read from `~/.config/workbench/claude-token` (mode 0600) and given to bwrap on a file descriptor after `--clearenv` (bwrap reads its options in order). In each mode it replaces each copy of that token in the step's stdout and stderr with `<redacted>`: the stream of a Claude step holds the tool results. A new wrapper passes the probe before its first step.

## Stops and the budget

A wait sets the status `waiting`, the tracker state `owner.waiting_state`, and 1 comment of at most `messages.max_chars` characters: the case, the question and the run folder.

| Case | When |
|---|---|
| 1 | The budget: before each step, dollars or time at `budget.stop_percent` of the limit; or a step that is `"unpriced"` |
| 2 | A decision: spec-check questions, a blocked build or rework, a step that fails twice, a failed push, a run that stops with an error |
| 3 | A High tier item before its build |
| 4 | The review still has blocking findings after the allowed rework rounds |

After each step the script adds its dollars; a step with no usage adds 0. The item time is the wall-clock time of `run-next`, without owner waits. At `budget.alert_percent` of a limit (dollars, time or rework rounds) the tracker gets 1 comment. A step's time limit is the smaller of `steps.max_seconds` and the time that is left. After each step the tracker field `tracker.subagent_cost_field` is the sum of the dollars of the steps.

## The commands of deliver

This repo ships no gate script, no host test, no review command and no tracker command for `deliver`: each is a command of your own, set as a list of words in the `[deliver]` table of the local `config/workbench.toml`. The example config keeps each list empty, and an empty list stops the run at its call. `wb` fills `{id}`, `{head}`, `{base}`, `{branch}` and `{pr}` in each word, runs the command with no shell in the work folder, within `deliver.command_seconds`, and keeps its stdout and stderr in `deliver/<head>/` of the item folder. It reads only the exit code and the lines below.

| Command | Called | Green, and what `wb` reads |
|---|---|---|
| `host_test` (`[deliver.default]` or `[deliver.<repos name>]`) | as set | Exit 0 and the last non-empty line of stdout `HOST-TEST: <head> PASS`. Lines of stdout that start with `SUITE` may hold `passed=<n>` and `failed=<n>`: `wb` sums them. A busy test host exits 2 and prints `refusing: no host-test slot` on stdout or stderr: `wb` waits `retry_seconds` and calls again, up to `slot_seconds` |
| `code_review`, `second_review` (the same tables) | as set; `second_review` not at Low tier | Exit 0 and the last line `CODE-REVIEW: <n> findings (<c> critical, <h> high, <m> medium, <l> low)` with 0 critical, 0 high and 0 medium. `second_review` may end with a line that starts with `UNAVAILABLE`; the gate judges it |
| `gate_source` | as set | Its stdout is the source of a Python gate script. `wb` writes it to `deliver/<head>/delivery_check.py` and runs it with its own Python: `delivery_check.py record --file <checks.jsonl> --sha <head> <check> <result>` for `tests` (`<n> passed`), `self-check`, `code-review`, `reviewer-review` and, when it ran, `second-review` (each result is the line of that check); `delivery_check.py record --file <checks.jsonl> --sha <head> --from-host-test <stdout file of the host test>`; each must exit 0. Then `delivery_check.py gate --item <id> --branch <branch> --tier <tier> --spec <spec path> --repo <work folder> --base <base>`: green is exit 0 and a line `DELIVERY-CHECK: PASS <branch> head=<head>`; else the first line that starts with `DELIVERY-CHECK:` is the reason of the stop |
| `ado` | 3 times, with the words `state <id> <review_state>`, `field <id> <tracker.subagent_cost_field> <file of the dollars>` and `comment <id> <HTML file>` added | Exit 0 each |

## Config

The keys of `config/workbench.example.toml` that the stage machine reads: `state.home`, `work.home`, `work.base`, `tracker.kind` (`local`), `steps.max_seconds`, `budget.alert_percent`, `budget.stop_percent`, `owner.waiting_state`, `messages.max_chars`, `specs.max_kb`, `tracker.subagent_cost_field`, `delivery.push_token_file`, `pages.theme_key`, `pages.ado_url`, `pages.time_zone`, `notify.command`, `notify.page_url`, `notify.quiet`, `notify.digests`, `notify.fyi_minutes`, `notify.remind_hours`, the `[runners.<name>]` tables, with their `guard` and `wrap`, and for `deliver` `deliver.retry_seconds`, `deliver.slot_seconds`, `deliver.command_seconds`, `deliver.review_state`, `deliver.gate_source`, `deliver.ado` and the lists `host_test`, `code_review` and `second_review` of `[deliver.default]` (an item with no `--repo`) or `[deliver.<repos name>]`. Each list is a command with no shell, run in the work folder with stdin the null device and a limit of `deliver.command_seconds`; wb fills `{id}`, `{head}`, `{base}`, `{branch}` and `{pr}` in each word. The hosts go in the local config only.

## Tests

```sh
python -m pytest tests/test_wb_*.py
```

The tests run every step on the fake runner, in a temporary git work tree; they call no model. The push tests use a local bare repository and a fake API, the wrapper tests a fake `bwrap`; no test pushes to GitHub. The page tests load an IANA zone other than UTC: on Windows, which has no zone database, install `tzdata` first, the `test` extra of `pyproject.toml`: `python -m pip install tzdata`.
